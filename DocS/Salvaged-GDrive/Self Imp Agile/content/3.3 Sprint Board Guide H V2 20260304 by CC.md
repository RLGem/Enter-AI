## TL;DR — כל מה שצריך לזכור

**הלוח הוא המוח המשותף של הצוות. אם זה לא על הלוח — זה לא קרה.**

- 5 עמודות: New → Active → In Review → Testing → Done
- כרטיס זז **ימינה בלבד**, רק כשסיים ממש את השלב — לא "כמעט"
- WIP Limits קיימים: אל תעקפו אותם
- עדכון יומי **לפני** ה-Daily — 2 דקות, לא אחריו
- פריט חסום? מסמנים `Blocked`, SM מטפל תוך 4 שעות

## 1. מה זה Sprint Board?

Sprint Board הוא **המפה החזותית של כל העבודה בספרינט**. בכל רגע נתון, כל אחד בצוות יכול להסתכל על הלוח ולהבין: מה הצוות עובד עליו, מה תקוע, מה הושלם, וכמה נותר.

הלוח הוא **מקור האמת היחיד** של הספרינט. לא המייל, לא הוואטסאפ, לא הזיכרון של מישהו. הלוח.

**למה זה עובד?**
כשהמידע גלוי לכולם, הצוות מזהה חסמים מוקדם יותר, עוזר אחד לשני בלי לחכות לישיבה, ולא מבזבז זמן ב-Daily על עדכונים שאפשר לקרוא בעצמך.

## 2. מבנה הלוח — 5 עמודות

</div>

```
+==========================================================================+
|                        SPRINT BOARD — 3-Week Sprint                      |
+==========================================================================+
|    New      |   Active    |  In Review  |   Testing   |     Done         |
|   (חדש)     |  (בעבודה)   | (סקירת קוד) |  (בבדיקות)  |    (הושלם)       |
|-------------|-------------|-------------|-------------|------------------|
|             |             |             |             |                  |
|  מה שתוכנן  | בעבודה עכשיו|  ממתין/ת   | בבדיקות     | הושלם ועמד       |
|  ועדיין לא  |   בצוות     | לסקירת קוד | ידניות /    | ב-DoD. נגמר.     |
|   התחיל     |             |  או PR פתוח | אוטומטיות   |                  |
|             |             |             |             |                  |
+==========================================================================+
```

<div dir="rtl">

| תיאור | עמודה |
|------:|------:|
| פריטים שתוכננו בספרינט ועדיין לא הוקצו לאף אחד. כאן ממתינים לתחילת העבודה. | **New** |
| פריטים שמישהו עובד עליהם כרגע. אם הפריט שלך כאן — תן לו את מלוא תשומת לבך. | **Active** |
| הקוד הושלם מהצד הטכני ו-PR פתוח. ממתין לסקירת קוד ואישור לפני הבדיקות. | **In Review** |
| הפריט עבר Code Review, מוזג, ועכשיו עובר בדיקות ידניות ו/או אוטומטיות. | **Testing** |
| הפריט עמד בכל קריטריוני ה-Definition of Done. גמור לגמרי. אל תיגעו בו. | **Done** |

> **כלל לזכור:** "כמעט סיימתי" = עדיין **Active**. רק כשהשלב הסתיים לגמרי — הכרטיס זז.

## 3. WIP Limits — למה הם קיימים ואיך מגדירים

WIP = Work In Progress. גבול WIP הוא מספר הפריטים המקסימלי שיכולים להיות בעמודה בו-זמנית.

**למה זה חשוב?**
כשאין גבולות, כולם מתחילים הכל ולא מסיימים כלום. המצב הגרוע ביותר הוא צוות שיש לו 12 פריטים "Active" ו-0 ב-Done באמצע הספרינט. זה לא עבודה מקבילה — זה אנדרלמוסיה.

**גבול WIP = לחץ בריא לסיים לפני שמתחילים משהו חדש.**

</div>

```
+===========================================+
|         WIP LIMITS — המלצה               |
+===========================================+
| עמודה      | גבול מומלץ    | דוגמה (4 devs)|
|------------|---------------|---------------|
| New        | ללא גבול      |       —       |
| Active     | 2 × מפתחים   |       8       |
| In Review  | 1 × מפתחים   |       4       |
| Testing    | 1 × מפתחים   |       4       |
| Done       | ללא גבול      |       —       |
+===========================================+
```

<div dir="rtl">

**מה עושים כשגבול WIP הושג?**
לפני שמתחילים פריט חדש — עזרו לזוז פריט שכבר In Review או Testing קדימה. **Stop Starting, Start Finishing.**

---

## 4. כללי הזזת כרטיסים

כרטיס זז ימינה **רק כשהשלב שלו הסתיים לגמרי**. לא "כמעט", לא "בעוד שעה", לא "לאחר שהם יאשרו". הסתיים — זז.

</div>

<div dir="rtl">

| האם מזיזים? | מצב |
|:----------:|----:|
| לא — נשאר Active | "כמעט סיימתי את הקוד" |
| כן — עובר In Review | "הקוד הושלם, PR פתוח ב-Azure DevOps" |
| לא — נשאר In Review | "הסתכלתי על ה-PR, יש לי הערות" |
| כן — עובר Testing | "PR אושר, נכנס ל-main branch" |
| לא — נשאר Testing | "הרצתי חלק מהבדיקות, לא הכל" |
| כן — עובר Done | "כל הבדיקות עברו, עמד ב-DoD המלא" |

> **כלל הזהב:** מי שעובד על הפריט — הוא/היא מזיז/ה את הכרטיס. לא ה-SM, לא ה-PO.

## 5. פריטים חסומים (Blocked Items)

חסם (Blocker) הוא כל דבר שמונע מפריט להתקדם: תלות בצוות אחר, המתנה להחלטה, גישה שלא ניתנה, באג חיצוני, בעיית תשתית.

**כלל:** אל תחכו לפתור לבד יותר מ-4 שעות. סמנו חסום ותנו ל-SM לטפל.

</div>

<div dir="rtl">

| פעולה | שלב |
|------:|----:|
| הוסף Tag: `Blocked` לפריט ב-Azure DevOps | **1. סמנו** |
| הכרטיס הופך אדום (Style Rule) — כולם רואים | **2. גלוי** |
| ציינו בכרטיס — בשורת Comment — מה בדיוק חוסם | **3. תעדו** |
| הודיעו ב-Daily הבא (או מיד אם דחוף) | **4. הודיעו** |
| SM מטפל ומסיר את ה-Tag כשנפתר | **5. פתרו** |

</div>

```
+==============================================+
|         ESCALATION PATH — חסמים             |
+==============================================+
| 4 שעות → הצוות מנסה לפתור ביחד            |
| 24 שעות → SM מסלים / פונה לגורם חיצוני    |
| 48 שעות → SM מסלים למנהלה                  |
+==============================================+
```

<div dir="rtl">

> **חסם שלא מדווח = חסם שלא נפתר.** ה-SM לא יכול לעזור לכם אם הוא/היא לא יודע/ת.

## 6. Swimlanes — נתיבי שחייה (אופציונלי)

Swimlanes הם שורות אופקיות בתוך הלוח שמאפשרות להפריד בין סוגי עבודה שונים.

</div>

<div dir="rtl">

| מתי להשתמש | תיאור | Swimlane |
|:----------:|------:|---------:|
| פריט דחוף במיוחד שחייב להסתיים תוך 24-48 שעות | פריט קריטי / Hot Fix | **Expedite** |
| באגים שמדווחים במהלך הספרינט ולא תוכננו מראש | תיקוני באגים | **Bugs** |
| עבודה על שיפור תשתית, ניקוי קוד, שדרוגים | השקעה ארוכת טווח | **Tech Debt** |

> **המלצה:** התחילו **בלי** Swimlanes. הוסיפו רק כשיש צורך אמיתי — יותר מדי Swimlanes הופכים את הלוח למבוך.

## 7. עדכון יומי — שגרת 2 הדקות

**כל בוקר, לפני ה-Daily Standup** (לא במהלכו, לא אחריו):

</div>

```
+===============================================+
|     DAILY BOARD UPDATE — 2 דקות              |
+===============================================+
| ✅ Tasks שסיימתם → העבירו ל-Done             |
| ✅ Tasks שהתחלתם → העבירו ל-Active           |
| ✅ Remaining Work → עדכנו שעות שנותרו        |
| ✅ חסמים → הוסיפו Tag "Blocked" + Comment    |
+===============================================+
```

<div dir="rtl">

**למה לפני ה-Daily ולא אחריו?**
כי ה-Daily הוא על הלוח — אם הלוח לא מעודכן, ה-Daily הופך לסיבוב דיווח פה לפה. כשהלוח מעודכן, ה-Daily קצר יותר ועוסק בבעיות אמיתיות.

**נתיב ב-Azure DevOps:**
`Boards → Sprints → [ספרינט נוכחי] → Taskboard`

## 8. "Walk the Board" — חלופה לסיבוב עגול

במקום שכל אחד/ת ידבר/ת לפי תור, **עוברים על הלוח מימין לשמאל** — מ-Done ל-New. הצוות מתמקד בעבודה, לא באנשים.

</div>

<div dir="rtl">

| שואלים | עמודה |
|-------:|------:|
| מה הושלם? אפשר לחגוג! | **Done** |
| מה נמצא בבדיקות? יש חסמים? מישהו צריך עזרה? | **Testing** |
| מה ממתין לסקירה? PR תקוע? מישהו פנוי לריוויו? | **In Review** |
| מה בעבודה? יש פריטים ש"תקועים" ב-Active יותר מ-2 ימים? | **Active** |
| מה עדיין לא התחיל? האם יש מישהו שיכול לקחת? | **New** |

> **מתי להשתמש ב-Walk the Board?** כשה-Daily הרגיל הפך לדיווח שגרתי ומשעמם, או כשיש הרבה פריטים ורוצים לוודא שכולם גלויים.

## לסיכום

הלוח הוא לא עוד כלי בירוקרטי — הוא **אמצעי תקשורת**. צוות שמסתכל על הלוח פעם ביום יודע בדיוק מה קורה בספרינט, איפה יש עומסים, איפה יש חסמים, ואיפה צריך עזרה.

שלושה כללים פשוטים:
1. **עדכנו כל יום** — לפני ה-Daily, 2 דקות
2. **כבדו WIP Limits** — אל תתחילו דברים חדשים כשיש פריטים ב-Review ו-Testing שצריכים אתכם
3. **דווחו על חסמים** — ה-SM לא יכול לעזור לכם אם הוא/היא לא יודע/ת

**הלוח הוא המוח המשותף של הצוות. אם זה לא על הלוח — זה לא קרה.**
