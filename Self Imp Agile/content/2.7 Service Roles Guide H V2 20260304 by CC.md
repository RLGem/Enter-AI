# מדריך לתפקידי שירות — Service Roles Guide

> **גרסה:** 2.0 | **תאריך:** 04.03.2026
> **קהל יעד:** ארכיטקט/ית, DBA, מערכות, DevOps — תפקידי שירות לצוותי Scrum
> **זמן קריאה:** 5 דקות

---

## TL;DR

1. **אתם לא חלק מצוות ה-Scrum.** אתם נותני שירות — הצוות קורא לכם כשהוא צריך אתכם.
2. **אתם לא צריכים להגיע לכל טקס.** רק כשיש פריט שנוגע לתחום שלכם.
3. **המטרה:** להגיע, לעזור, לחזור לעבודה. בלי ישיבות מיותרות, בלי בירוקרטיה.

---

## 1. מה זה אומר בשבילך

המעבר ל-Agile לא מוסיף לך ישיבות. הוא בעצם **מסדר** את הזמן שאתה כבר נותן לצוותים.

**עד עכשיו:**
- מפתח שולח מייל, אתה עונה מתישהו
- בקשות מגיעות ללא הקשר — "צריך DB חדש, דחוף"
- אין לך מושג מה הצוות עושה ומתי הם צריכים אותך

**עכשיו:**
- הצוות עובד בספרינטים של **3 שבועות** עם קצב קבוע
- בקשות מגיעות עם **הקשר** — User Story, קריטריונים, תאריך יעד
- אתה יודע מראש **מתי** צפויים לפנות אליך

שלושה דברים שכדאי להבין:

| מה :| למה :|
|---:|---:|
| הצוות עובד בספרינטים של 3 שבועות | כדי שתדע את הקצב — מתי מתכננים, מתי מפתחים, מתי עולים לאוויר |
| יש Backlog Refinement באמצע הספרינט | זה המקום שבו יגלו שהם צריכים אותך לספרינט הבא |
| הצוות מחליט מתי למשוך אותך פנימה | אתה לא צריך לעקוב — הם יפנו אליך |

## 2. הספרינט בן 3 השבועות — מתי יצטרכו אותך

```
ספרינט בן 3 שבועות — נקודות מגע לתפקידי שירות
═══════════════════════════════════════════════════════════════════════

        │ שבוע 1              │ שבוע 2              │ שבוע 3
        │ Planning + התחלה    │ פיתוח + Refinement   │ סיום + Review
────────┼─────────────────────┼─────────────────────┼─────────────────
ארכיטקט │                     │ ▲ Refinement —       │
        │                     │   פריטים עם השפעה    │
        │                     │   ארכיטקטורית         │
────────┼─────────────────────┼─────────────────────┼─────────────────
DBA     │                     │ ▲ אמצע ספרינט —     │
        │                     │   שינויי סכמה,       │
        │                     │   Queries, ביצועים    │
────────┼─────────────────────┼─────────────────────┼─────────────────
מערכות  │ ▲ הקמת סביבה        │                     │ ▲ תמיכה בפריסה
(Sys-   │   (אם נדרש)         │                     │   לסביבת בדיקות
Admin)  │                     │                     │   או Production
────────┼─────────────────────┼─────────────────────┼─────────────────
DevOps  │ ▲ Pipeline —        │ ▲ תיקון Pipeline     │ ▲ פריסה סופית,
        │   בדיקת תקינות      │   אם נשבר           │   Release
────────┼─────────────────────┼─────────────────────┼─────────────────

▲ = נקודת מגע צפויה — הצוות יפנה אליך
```

<div dir="rtl">

> **שים לב:** אלה הנקודות **הצפויות**. הצוות יכול לפנות אליך בכל רגע — אבל ברוב המקרים, זה יהיה בחלונות האלה.

## 3. מתי יפנו אליך — לפי תפקיד

### ארכיטקט/ית מערכת (System Architect)

| מתי :| מה יבקשו :| איך להתכונן :|
|---:|---:|---:|
| תחילת פרויקט | הגדרת ארכיטקטורה ראשונית, בחירת טכנולוגיות | הכר את ה-Product Vision ואת ה-Backlog הראשוני |
| Backlog Refinement (שבוע 2) | סקירת פריטים עם השפעה ארכיטקטורית — API חדש, שינוי מבנה, אינטגרציה | בקש מה-PO מראש את רשימת הפריטים שנוגעים לתחומך |
| בעיה טכנית חוצת ספרינטים | החלטה על Trade-off — ביצועים מול זמן, Refactor מול Workaround | תעד החלטות ב-Wiki או כ-ADR (Architecture Decision Record) |

**המפתח שלך:** Refinement הוא הטקס שהכי רלוונטי לך. אם את/ה משתתף/ת בטקס אחד — זה הוא.

---

### DBA

| מתי :| מה יבקשו :| איך להתכונן :|
|---:|---:|---:|
| אמצע ספרינט (שבוע 2) | שינויי סכמה, אינדקסים, Stored Procedures, אופטימיזציה | בדוק שיש לך גישה לסביבת הפיתוח של הצוות |
| לפני פריסה (שבוע 3) | סקריפטים של Migration, בדיקת ביצועים על נתוני בדיקה | וודא שה-Migration Scripts עוברים ב-Staging לפני Production |
| Refinement (לפי הצורך) | הערכת מורכבות של פריטים עם שינוי DB | אם הזמינו — הגע. אם לא — לא צריך |

**המפתח שלך:** הצוות ילמד לתכנן שינויי DB כ-User Stories עם Acceptance Criteria. זה יקל עליך.

---

### מנהל/ת מערכות (SysAdmin)

| מתי :| מה יבקשו :| איך להתכונן :|
|---:|---:|---:|
| תחילת פרויקט / ספרינט ראשון | הקמת סביבות (Dev, Test, Staging) | בדוק דרישות מול ה-DevOps Engineer |
| שבוע 3 — לפני Review | פריסה לסביבת בדיקות או Production | וודא שה-Checklist לפריסה מוכן ומתואם עם DevOps |
| פניות אד-הוק | בעיות הרשאות, שרתים, תקלות סביבה | הגדר ערוץ תקשורת ברור (Teams, טלפון) כדי שלא תקבל מיילים "דחופים" בלי הקשר |

**המפתח שלך:** ככל שהסביבות מוכנות מראש, תקבל פחות פניות באמצע הספרינט.

---

### DevOps Engineer

| מתי :| מה יבקשו :| איך להתכונן :|
|---:|---:|---:|
| תחילת ספרינט (שבוע 1) | בדיקת Pipeline — Build, Test, Deploy תקינים | הכר את ה-Repo ואת ה-Branch Strategy של הצוות |
| אמצע ספרינט | תיקון Pipeline שנשבר, הוספת שלבים (Lint, Security Scan) | הגדר התראות אוטומטיות כדי שתדע על כישלון לפני שהצוות מתקשר |
| סוף ספרינט (שבוע 3) | פריסה סופית, Release Notes, תיוג גרסה | וודא ש-Release Pipeline עובד ב-Staging לפני Production |

**המפתח שלך:** אוטומציה טובה = פחות פניות. ככל שה-CI/CD יציב — הם יצטרכו אותך פחות, וזה מצוין.

## 4. מה כן ומה לא

| כן :| לא :|
|---:|---:|
| הגע כשהצוות מזמין | אל תשב בכל Daily Standup |
| תן הערכת זמן כשמבקשים | אל תקח על עצמך Tasks בלי תיאום עם ה-SM |
| תעד החלטות טכניות שקיבלת | אל תשנה ארכיטקטורה/סביבה בלי לעדכן את הצוות |
| הגדר SLA ברור — "פונים אליי ב-X, אני עונה תוך Y" | אל תהיה צוואר בקבוק — אם אתה עמוס, תגיד |
| בקש הקשר — "איזה User Story זה משרת?" | אל תעשה עבודה "בשקט" שתפתיע את הצוות ב-Review |

## 6. הצעד הבא

1. **דבר עם ה-Scrum Master** של הצוות שאתה משרת — שאל: "מתי ה-Refinement הבא? יש פריטים שנוגעים לתחום שלי?"
2. **הגדר SLA** — הודע לצוות: "פנו אליי ב-Teams, אני מתחייב לחזור תוך [X שעות]."
3. **זהו.** חזור לעבודה.

---
