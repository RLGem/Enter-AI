# מדריך Definition of Done — הגדרת "גמור" שכולם מסכימים עליה

> **גרסה:** 2.0 | **תאריך:** 04.03.2026
> **קהל יעד:** מפתחים + Scrum Masters
> **זמן קריאה:** 4 דקות
> **סביבת עבודה:** Azure DevOps | ספרינטים של 3 שבועות

---

## TL;DR — הנקודה בשורה אחת

**"גמור" לא אומר 'כתבתי קוד'.**
**"גמור" אומר — עובד, נבדק, עבר Review, ונפרס.**

אם לפחות קריטריון אחד לא מולא — זה **לא Done**. לא "כמעט", לא "חוץ מ". פשוט — לא Done.

---

## 1. למה DoD חשוב — בלעדיו ה-Review הופך לכאוס

</div>

יום חמישי, 15:00. Sprint Review. מיכל, ה-PO, מכינה את ה-Demo.
הפיצ'ר לא ב-Staging.

"יוסי, אמרת שסיימת?"
"כן — כתבתי את הקוד. Deploy עוד לא עשיתי."
"ו-Code Review?"
"לא הספקתי..."

<div dir="rtl">

**זה לא קורה כי יוסי רשלן. זה קורה כי לא הייתה הגדרה מוסכמת למילה "גמור".**

ה-Definition of Done (DoD) היא רשימת תיוג שהצוות כותב ומסכים עליה יחד — ומגדירה בדיוק מה חייב לקרות לפני שאפשר להגיד "Done".

</div>

<div dir="rtl">

| עם DoD | בלי DoD |
|--------:|---------:|
| "גמור" = הגדרה אחת לכולם | "גמור" = כל אחד מתכוון למשהו אחר |
| באגים נמצאים בזמן הפיתוח | באגים מתגלים ב-Review מול הלקוח |
| Increment שאפשר להדגים ולשלוח | Increment שמפחיד לגעת בו |
| PO יכול לסמוך על "סיימתי" | PO צריך לאמת כל דבר בעצמו|

</div>

## 2. ארבע רמות של DoD

כל רמה בונה על הרמה שמתחתיה. לא ניתן לקפוץ.

</div>

<div dir="rtl">

| מי בודק | מתי | רמה |
|--------:|-----:|-----:|
| המפתח/ת + סוקר/ת (Code Review) | כשמעבירים Task ל-Done | **Task** |
| PO + מפתח/ת | כשכל ה-Tasks של ה-Story הושלמו | **Story** |
| SM + הצוות | יום לפני ה-Sprint Review | **Sprint** |
| PO + SM + QA | לפני Deploy ל-Production | **Release** |

</div>

---

<div dir="rtl">

### רמה 1 — Task DoD

</div>

```
Definition of Done — Task
─────────────────────────
- [ ] קוד נכתב ועובר Compilation ללא שגיאות
- [ ] Unit Tests כתובים ועוברים (כיסוי תרחישים עיקריים)
- [ ] קוד עבר Code Review ואושר על ידי מפתח/ת אחד/ת לפחות
- [ ] תיעוד עודכן אם רלוונטי (README, הערות בקוד, API docs)
- [ ] הקוד מוכן ל-Merge — אין Conflicts עם ה-Branch הראשי
```

---

<div dir="rtl">

### רמה 2 — Story DoD

</div>

```
Definition of Done — Story
──────────────────────────
- [ ] כל ה-Tasks הושלמו ועומדים ב-Task DoD
- [ ] Acceptance Criteria — כל הקריטריונים מאומתים ועוברים
- [ ] בדיקות אינטגרציה (Integration Tests) עוברות
- [ ] נפרס לסביבת Dev/Staging בהצלחה
- [ ] PO אישר את הפיצ'ר בסביבת הבדיקות
- [ ] אין באגים פתוחים בחומרה גבוהה (Critical/High) הקשורים ל-Story
```

---

<div dir="rtl">

### רמה 3 — Sprint DoD

</div>

```
Definition of Done — Sprint
───────────────────────────
- [ ] כל ה-Stories שנכנסו לספרינט עומדים ב-Story DoD
- [ ] Sprint Review בוצע — הודגמה תוכנה עובדת
- [ ] Sprint Retrospective בוצע — Action Items מתועדים ב-Azure DevOps
- [ ] Burndown Chart מעודכן ומשקף את המצב הסופי
- [ ] אין Work Items תקועים בסטטוס Active (הכל Done או חזר ל-Backlog)
```

---

<div dir="rtl">

### רמה 4 — Release DoD

</div>

```
Definition of Done — Release
────────────────────────────
- [ ] כל ה-Stories המיועדים ל-Release עברו QA בסביבת Staging
- [ ] בדיקות רגרסיה (Regression Tests) עברו בהצלחה
- [ ] Release Notes מוכנים — רשימת שינויים ברורה
- [ ] תוכנית Rollback קיימת ומתועדת — מה עושים אם משהו נשבר
- [ ] PO אישר את הגרסה לפני השחרור
```

## 4. מי הבעלים של ה-DoD?

**הצוות.** לא המנהל/ת. לא ה-PO בלבד. לא ה-SM לבד.

</div>

<div dir="rtl">

| האחריות | מי |
|--------:|----:|
| **הצוות** יוצר ומעדכן — ה-DoD הוא ההסכם הפנימי שלו | **בעלות** |
| **SM** מוודא שה-DoD קיים, מוסכם, וגלוי (Wiki / לוח) | **תחזוקה** |
| **PO** מגדיר Acceptance Criteria לכל Story — אלה הם חלק מה-Story DoD | **קלט** |
| **מנהל/ת** מכבד/ת את ה-DoD ולא מלחיץ/ה לדלג עליו תחת לחץ | **תמיכה** |

</div>

<div dir="rtl">

> **כלל אחד:** אם ה-DoD נכתב בידי גורם אחד שאחרים לא היו שותפים לו — הוא לא יאוכף. DoD שהצוות כתב יחד — יאוכף.

---

## 5. מתי מעדכנים DoD?

**ב-Retrospective — כל ספרינט.**

בכל Retro, שאלו: "האם ה-DoD שלנו עדיין מגן עלינו? מה כאב הספרינט הזה שה-DoD לא תפס?"

</div>

<div dir="rtl">

| מה עושים | מתי |
|----------:|-----:|
| שואלים: "האם ה-DoD שלנו מספיק? מה חסר?" | **כל Retro** |
| מוסיפים סעיף שמונע את הבעיה מלחזור | **כשכאב** |
| שוקלים הסרה רק אם הסעיף הפך אוטומטי לחלוטין (CI/CD) | **כשאוטומטי** |

</div>

<div dir="rtl">

**דוגמה — DoD שמתפתח לאורך ספרינטים:**

ספרינט 1: באגים התגלו כי לא עשינו Deploy ל-Staging → הוסיפו סעיף.
ספרינט 2: PO גילה שפיצ'ר לא עונה על הדרישות → הוסיפו "PO אישר".
ספרינט 3: DoD חזק יותר, Review חלק יותר, אמון גדול יותר.

## 6. טעויות נפוצות — ואיך להימנע מהן

</div>

<div dir="rtl">

| איך מתמודדים | הטעות |
|-------------:|-------:|
| DoD תלוי על הקיר — כולם רואים אותו לפני כל Merge | **מעבירים ל-Done לפני שעמדו בכל הסעיפים** |
| SM מזכיר/ה ב-Planning: "יש לנו DoD אחד לכולם, לא לכל אחד" | **כל מפתח/ת מחיל/ה DoD שונה** |
| SM מנחה כתיבת DoD ב-Sprint 1, אפילו אם פשוט | **אין DoD בכלל** |
| DoD בוחן שהדברים עובדים — לא שהם מושלמים. אם יש יותר מ-7 סעיפים בטאסק — סמנו מה חובה | **DoD נוקשה מדי שמאט הכל** |
| SM מזכיר/ה: "לחץ הוא הסיבה להחיל DoD, לא לוותר עליו" | **מדלגים על DoD תחת לחץ** |

</div>
