## TL;DR — כל מה שצריך לזכור

**מודדים כדי להשתפר, לא כדי לשפוט. מדדי צוות בלבד — לעולם לא מדדים אישיים.**

- **Burndown Chart** — מה נותר השבוע? הולך לכיוון הנכון?
- **Velocity** — ממוצע 3 ספרינטים. משתמשים לתכנון, לא להשוואה
- **Cycle Time** — מ-Active ל-Done. יעד: יורד עם הזמן
- **CFD** — פס שמתרחב = צוואר בקבוק. פועלים מיד
- **Dashboard:** Burndown + Velocity + Sprint Overview + CFD
- מדדים אישיים? שורות קוד? שעות עבודה? **לא. אף פעם.**

> "מספרים מספרים סיפור. תוודאו שזה הסיפור הנכון. לעולם אל תשתמשו במדדים כנשק."

## 1. ארבעת המדדים המרכזיים

### 1.1 Burndown Chart — מה נותר?

**מה זה:** גרף שמראה כמה עבודה **נותרה** לאורך הספרינט. ציר X = ימים, ציר Y = שעות (Remaining Work) או Story Points.

הגרף כולל שני קווים:
- **קו אידיאלי** — ירידה אחידה מהיום הראשון ועד לאפס ביום האחרון
- **קו בפועל** — מה שקורה במציאות

**הפער בין הקווים הוא הסיפור.**

</div>

```
+------------------------------------------+
|         BURNDOWN CHART — ספרינט בריא     |
+------------------------------------------+
  שעות
  נותרו
   120 |*
       | \  *
    90 |  \   *
       |   \    *
    60 |    \     *
       |     \      *
    30 |      \       *
       |       \        *
     0 |________\________*_____
       ש1  ש3  ש5  ש7  ש9  ש11 ש13 ש15

       \ = קו אידיאלי    * = קו בפועל
```

<div dir="rtl">

**ארבעה דפוסים שחייבים להכיר:**

</div>

```
+--------------------------------------------------+
| דפוס           | מה רואים         | משמעות       |
|----------------|------------------|--------------|
| בריא           | עוקב את הקו      | הצוות מתקדם  |
|                | האידיאלי         | בקצב יציב    |
|----------------|------------------|--------------|
| התחלה מאוחרת  | שטוח בהתחלה,     | Stories גדולים|
|                | צלילה בסוף       | מדי / WIP גבוה|
|----------------|------------------|--------------|
| Scope Creep    | הקו עולה למעלה   | נוספה עבודה  |
|                |                  | בלי אישור    |
|----------------|------------------|--------------|
| מצוק (Cliff)   | שטוח לאורך כל    | הבורד לא     |
|                | הספרינט, צלילה   | מעודכן — SM  |
|                | ביום האחרון      | צריך לפעול   |
+--------------------------------------------------+
```

<div dir="rtl">

**איך לפתוח ב-Azure DevOps:**
Boards → Sprints → ספרינט נוכחי → לשונית **Sprint Burndown**

> **המלצה:** מדדו לפי **Remaining Work (שעות)** — נותן את התמונה המדויקת ביותר יום-יום.

### 1.2 Velocity — כמה הצוות מסיים?

**מה זה:** כמות Story Points שהצוות **הגיעה ל-Done** בספרינט. לא מה שהתחילו — מה שסיימו לגמרי.

**כלל הזהב: Velocity = כלי תכנון. לא כלי ביצועים.**

מחשבים **ממוצע גלגלי של 3 ספרינטים אחרונים** — זה המספר שאתם מביאים ל-Planning:

</div>

```
+--------------------------------------------------+
|          VELOCITY — ממוצע 3 ספרינטים            |
+--------------------------------------------------+
| ספרינט       | תוכנן (SP) | הושלם (SP) | הפרש   |
|--------------|------------|------------|--------|
| Sprint N-2   |     28     |     24     |   -4   |
| Sprint N-1   |     26     |     27     |   +1   |
| Sprint N     |     27     |     26     |   -1   |
|--------------|------------|------------|--------|
| ממוצע Velocity:           |    25.7 SP |        |
| → מביאים לספרינט הבא:    | כ-25–26 SP |        |
+--------------------------------------------------+
```

<div dir="rtl">

**מה בריא:**
- **יציבות עם מגמת עלייה קלה** — זה הסימן לצוות שמתלכד
- תנודות קטנות (±3–4 SP) — טבעי לחלוטין
- עלייה אחרי שיפור תהליך — Refactoring שעשיתם, Refinement שהשתפר

**מה מדאיג:**

</div>

```
+--------------------------------------------------+
| דפוס              | סימן אזהרה      | לחקור ב:   |
|--------------------|-----------------|------------|
| ירידה מתמדת        | 30→27→24→20    | Retro מיד  |
| תנודות חריפות      | 20→35→15→40    | Refinement |
| עלייה חדה פתאומית  | 25→25→25→45    | DoD נשמר?  |
| אפס תנודה לחלוטין  | 25→25→25→25    | כנות? לחץ? |
+--------------------------------------------------+
```

<div dir="rtl">

> **חוק ברזל: אסור להשוות Velocity בין צוותים.** Story Points הם יחידה יחסית שכל צוות מגדיר לעצמו. "30 SP" של צוות א' אינם שווים ל-"30 SP" של צוות ב'. זה כמו להשוות שטרות של מטבעות שונות — המספר זהה, הערך שונה.

### 1.3 Cycle Time — כמה זמן לוקח לפריט לזוז?

**מה זה:** הזמן שעובר מהרגע שמתחילים לעבוד על פריט (Active) עד שהוא Done. לא כולל זמן המתנה ב-Backlog.

</div>

```
+----------------------------------------------------+
|              CYCLE TIME — מדידה                   |
+----------------------------------------------------+

     New          Active         Resolved        Done
      |              |               |             |
      |              |<-- Cycle Time ------------>|
      |              |               |             |
      +              +               +             +
   נוצר         התחילו          פיתוח הסתיים    הושלם לגמרי
                לעבוד            ו-Review        לפי DoD
```

<div dir="rtl">

**למה זה חשוב:** Cycle Time מודד **צפיות (Predictability)**. כשלקוח שואל "מתי הפיצ'ר יהיה מוכן?" — Cycle Time הוא הבסיס לתשובה.

</div>

```
+----------------------------------------------+
| שאלה                     | מדד המענה        |
|--------------------------|------------------|
| "כמה נספיק בספרינט הבא?" | Velocity          |
| "מתי הפיצ'ר הזה יהיה    | Cycle Time        |
|  מוכן?"                  |                  |
+----------------------------------------------+
```

<div dir="rtl">

**יעד: Cycle Time יורד מספרינט לספרינט.**

אם Cycle Time ממוצע גדול מ-5 ימים — ה-Stories שלכם כנראה גדולים מדי.
אם גדול מ-8 ימים — יש חסמים מערכתיים שדורשים טיפול.

**איך מורידים Cycle Time:**
- פיצול Stories ל-Refinement (Stories קטנים מסיימים מהר יותר)
- הגבלת WIP — פחות עבודה במקביל = כל פריט מסתיים מהר יותר
- SM מטפל בחסמים תוך 4 שעות
- Code Review תוך יום עבודה אחד — זה נורמה, לא בקשה

### 1.4 Cumulative Flow Diagram (CFD) — זרימה או בוץ?

**מה זה:** גרף שטחי שמראה כמה פריטים נמצאים **בכל סטטוס** כל יום. כל סטטוס = פס צבע. הפסים נערמים.

**הכלל הפשוט: פסים מקבילים = בריא. פס שמתרחב = בעיה.**

</div>

```

  20 |DDDDDDDDDDDDDDDDDDDDDDDDDDDDDDD
     |DDDDDDDDDDDDDDDDDDDDDDDDDDD  RRRRR
  15 |DDDDDDDDDDDDDDDDDDDDDDDD  RRRRRRRRRRR
     |DDDDDDDDDDDDDDDDDDD  RRRRRRRRRRRRRRRR
  10 |DDDDDDDDDDDDDDDD  RRRRRRR  AAAAAAAAAA
     |DDDDDDDDDDDDDDD  RRRRRR  AAAAAAAAAAAAA
   5 |DDDDDDDDDDDD  RRRRR  AAAAA  NNNNNNNNNN
     |DDDDDDDDD  RRRRR  AAAAA  NNNNNNNNNNNNNN

     י1   י3   י5   י7   י9  י11  י13  י15

     N=New  A=Active  R=Resolved  D=Done
```

+--------------------------------------------------+
```

## 3. מדדים מסוכנים — מה אסור למדוד

> "ברגע שמדד הופך ליעד, הוא מפסיק להיות מדד טוב." — חוק גודהארט

כשמפתח/ת יודע/ת שנמדדים עליו/ה אישית — הוא/היא מפסיק/ה לעבוד ומתחיל/ה לנהל את המדד. הצוות מפסיד, האמון מתפרק, והמדד מאבד כל משמעות.

**ארבעה מדדים שהורסים צוותים:**

</div>

```
+----------------------------------------------------------+
|    מדדים מסוכנים — אל תמדדו את אלה                     |
+----------------------------------------------------------+
| מדד              | למה מסוכן          | מה קורה בפועל   |
|------------------|--------------------|-----------------|
| Velocity אישית   | הורג שיתוף פעולה  | אף אחד לא עוזר |
| (לפי מפתח)       | ● יוצר תחרות       | לעמיתים         |
|                  | רעילה              |                 |
|------------------|--------------------|-----------------|
| שורות קוד        | מתגמל ניפוח        | קוד מנופח,      |
| (Lines of Code)  | ● מעניש Refactoring| Refactoring     |
|                  |                    | נעצר            |
|------------------|--------------------|-----------------|
| שעות עבודה       | מעניש יעילות       | אנשים עובדים    |
| (Hours Worked)   | ● שוחק אנשים       | לאט כדי         |
|                  |                    | "להיראות עסוקים"|
|------------------|--------------------|-----------------|
| באגים למפתח      | יוצר תרבות         | מסתירים באגים,  |
| (Bugs per Dev)   | האשמה              | מפחדים לגעת     |
|                  | ● מעניש אומץ       | בקוד מורכב      |
+----------------------------------------------------------+
```

<div dir="rtl">

**המבחן המהיר — האם המדד בטוח?**

לפני שמחליטים למדוד משהו, שאלו שלוש שאלות:

</div>

```
+----------------------------------------------------------+
| שאלה                     | תשובה בטוחה  | תשובה מסוכנת |
|--------------------------|--------------|--------------|
| מי רואה את המדד?         | הצוות בלבד   | ההנהלה, לדרוג|
| ברמת מי מודדים?          | ברמת צוות    | ברמת אדם     |
| אפשר "לשחק" את המדד?     | לא הגיוני    | קל, ויש תמריץ|
+----------------------------------------------------------+
```

<div dir="rtl">

> אם תשובה אחת מהן מסוכנת — **אל תמדדו**. מדד רע גרוע מאין מדד.

## 5. מדדים בטקסים — מתי ומה מראים

**כל טקס משתמש במדדים אחרת. הנה הכלל לכל אחד:**

</div>

```
+----------------------------------------------------------+
|  טקס         | מה מראים          | מה שואלים          |
|--------------|-------------------|--------------------|
| Sprint       | Burndown של        | "האם הגענו         |
| Review       | הספרינט שנגמר      | ל-Sprint Goal?     |
|              | Velocity החדשה     | מה הראנו ללקוח?"   |
|              |                   |                    |
| Sprint       | Velocity (3 ספר') | "מה הצוות יכול     |
| Planning     | Capacity הספרינט  | לקחת לספרינט       |
|              |                   | הזה בצורה         |
|              |                   | ריאליסטית?"        |
|              |                   |                    |
| Retrospective| Velocity מגמה     | "מה המספרים        |
|              | Cycle Time מגמה   | אומרים לנו?        |
|              | CFD — אם יש דפוס | מה להשתפר?"        |
+----------------------------------------------------------+
```

<div dir="rtl">

**עקרון:** ב-Review מראים **מה עשינו**. ב-Planning משתמשים ב**מה יכולים**. ב-Retro מפרשים **מה למדנו**.

3. "אני SM. רואה ב-CFD שהפס של Resolved מתרחב. מה זה אומר ומה עושים?"

4. "אני SM. ה-Cycle Time עלה מ-3 ימים ל-7 ימים בספרינט האחרון. מה גורם
   לזה ואיך מטפלים?"

5. "אני SM. רוצה להגדיר Dashboard ב-Azure DevOps עם 4 Widgets מרכזיים.
   תן לי צ'קליסט הגדרה."

6. "אני SM. צריך/ה להציג את המדדים ב-Retro מחר. תן לי תסריט לאיך
   להציג Velocity + Cycle Time בצורה שמוביל לדיון פורה — לא להאשמות."
```
